Empirical Science
Give the history briefly. In 2008 Andrew Clay Shafer proposed a session on agile infrastructure at the Agile conference in Toronto, and Patrick Debois was the one person who attended. In June 2009 Allspaw and Hammond showed at the Velocity conference that Flickr deployed more than ten times a day because developers and operations engineers worked together and shared tools. Debois then organised devopsdays in Ghent in October 2009, and the short name stuck. The movement grew out of agile software development. Agile had shortened development cycles, but releases still waited weeks for operations. The books and the research came later and gave the practices a vocabulary and evidence. Sources: Allspaw and Hammond (2009); Kim et al. (2021), introduction.

The problem DevOps addresses

The two groups have opposite goals, and work moves between them in large, slow batches. DevOps practices give both groups one shared goal, which is frequent and safe change.

Describe the situation many organisations were in before DevOps. Development teams are measured on delivering features. Operations teams are measured on uptime. Every release is a risk to operations, so operations slows releases down, and development responds by bundling more changes into each release. Large releases fail more often and are harder to debug. The feedback loop is slow: a developer hears about a production problem weeks later, when the code is no longer fresh in their mind. Ask the class whether they recognise this pattern from mainframe or operations work. Many will. Source: Kim et al. (2021), part 1, "the core, chronic conflict".

The Three Ways

The Three Ways are the principles behind most DevOps practices (Kim et al., 2021).

The DevOps Handbook organises the practices under three principles. The First Way is flow: make work move quickly from left to right, from a developer's idea to a customer, in small batches, with as little waiting as possible. Continuous integration and deployment pipelines belong here. The Second Way is feedback: detect problems where they happen and send the information back quickly. Automated tests, monitoring and pull request checks belong here. The Third Way is continual learning and experimentation: blameless reviews of incidents, time to improve the system, and safe experiments. Today's labs mostly cover the First and Second Ways. Source: Kim, Humble, Debois, Willis and Forsgren (2021), The DevOps Handbook, 2nd edition, parts 2 to 5.

Value streams and lead time

Lead time for changes is the time from commit to running in production (Forsgren et al., 2018). In this example the change spends most of its lead time waiting.

A value stream is the sequence of activities that turns a request into something a customer uses. Value stream mapping records, for each activity, the work time and the waiting time before it. In this made-up example a change needs six and a half hours of work but takes about nine days to reach production, because it waits in queues: for a reviewer, for a test environment, for a change approval board, for a release window. Improving the speed of individual people barely changes the lead time. Removing waits does. Automation removes many of these waits: tests run when the code is pushed, and deployment does not need a scheduled window. Ask the class where changes wait longest in their own process. Sources: Kim et al. (2021), chapter 7; Forsgren, Humble and Kim (2018), chapter 2.

Batch size and work in progress

Large Batches

High Risk
  • × Long testing and verification cycles
  • × Fails more frequently with high blast radius
  • × Complex, time-consuming root cause debugging
  • × Painful, high-conflict merge sessions

Small Batches

Low Risk
  • ✓ Fast, actionable developer feedback loops
  • ✓ Contained blast radius on unexpected failure
  • ✓ Trivial to isolate defects and roll back
  • ✓ Frictionless, frequent trunk integration
Little's Law (Operations Research, 1961) Average Lead Time = Work in Progress (WIP) ÷ Throughput

Example: 20 items in progress ÷ 5 items finished per week = 4 weeks lead time.
Takeaway: To shorten lead time without working faster or cutting corners, start fewer things at once.

Batch size is one of the main ideas of lean manufacturing that DevOps applies to software. When a release contains two hundred changes and something breaks, the team must search two hundred changes for the cause. When a release contains one change, the cause is obvious and the rollback is small. Little's Law comes from queueing theory. It holds for any stable system: the average time an item spends in the system equals the number of items in the system divided by the rate at which items leave. The practical result: to shorten lead time without working faster, start fewer things at once. This is why trunk-based development and small pull requests matter, which is the next lecture. Sources: Little, J. D. C. (1961), Operations Research 9(3); Kim et al. (2021), chapter 2.

Measuring delivery performance

MetricQuestion it answersMeasures
Deployment frequencyHow often do we deploy to production?Throughput
Lead time for changesHow long does a commit take to reach production?Throughput
Change failure rateWhat share of deployments cause a failure in production?Stability
Failed deployment recovery timeHow long does it take to recover from a failed deployment?Stability

These are the DORA metrics (Forsgren et al., 2018). The 2024 DORA report adds a fifth measure, rework rate, which is the share of deployments that are unplanned fixes for production problems.

DORA stands for DevOps Research and Assessment. The research started with the State of DevOps reports in 2014 and is now run by Google Cloud. The four metrics measure software delivery, not individual people. Two measure throughput and two measure stability. The fourth metric was called "time to restore service" until 2023, when DORA renamed it to failed deployment recovery time to make clear it measures recovery from a change, not every kind of outage. DORA's current names are change lead time and change fail rate. Warn against using the metrics to compare teams or to set individual targets. Teams then change how they count instead of how they work. Sources: Forsgren, Humble and Kim (2018), chapter 2; DORA (2024), Accelerate State of DevOps Report.

What the research found

Finding 1

The False Trade-Off

Speed & Stability Go Together

High performers deploy faster and fail less often. Throughput and stability reinforce each other—small, frequent changes are inherently safer.

Finding 2

Commercial Impact

Directly Predicts Success

Software delivery performance directly drives organizational outcomes: profitability, market share, customer satisfaction, and operational efficiency.

Finding 3

Causal Drivers

Proven Engineering Practices

Trunk-based development, continuous integration, comprehensive test automation, and automated deployment causally predict high delivery performance.

Source: Accelerate (Forsgren, Humble & Kim, 2018) — Empirical research across 23,000+ industry respondents.
Accelerate summarises four years of State of DevOps research, from 2014 to 2017. The first finding surprises many people: the teams that deploy most often also have the lowest change failure rates and recover fastest. Small, frequent, automated changes are safer than large, rare, manual ones. The second finding links software delivery to the business. The third identifies capabilities that predict performance. The book lists twenty-four. Several of them are the topics of this course: version control of everything, trunk-based development, continuous integration, test automation, deployment automation and shifting security left. Point out that the research measures correlation and uses statistical methods to support the predictions, which the book explains in part two. Source: Forsgren, Humble and Kim (2018), chapters 2, 3 and 4.

Version Control and Continuous Integration

Branching workflows, trunk-based delivery, and automated checks

Topic transition: Version Control and Continuous Integration. This divider slide has zero allocated teaching time.

What version control records

  • A commit is a snapshot of all files, plus the author, time, message and parent commit.
  • Git names each commit by a hash of its content and its parents. Changing anything changes the hash.
  • A branch is a name that points to one commit. A merge commit has two parents.
Most participants use Git, but it helps to state the model precisely because pipelines depend on it. A commit stores a complete snapshot of the project, not a diff. Git computes a hash from the snapshot, the metadata and the parent hashes. Because the parent hash is part of the input, a commit hash identifies the whole history before it. If anyone rewrites an old commit, every later hash changes. This is why a pipeline can report a result for an exact commit and nobody can change that commit afterwards. A branch is a movable pointer. When you commit on a branch, the pointer moves to the new commit. In the diagram the feature branch started at 7c02, received two commits, and was merged into main. Source: Chacon and Straub, Pro Git, 2nd edition, chapter 3 (git-scm.com/book).

Two branching strategies

Git Flow (Driessen, 2010)Trunk-based development
Long-lived branchesmain, develop, release and hotfix branchesmain only
Feature branchesLast until the feature is finished, often weeksLast for hours, at most one or two days
When work is integratedWhen a feature branch mergesAt least once a day
ReleasesPrepared on a release branchMade from main at any time

The labs use trunk-based development with short-lived branches and pull requests.

Git Flow was published by Vincent Driessen in 2010 and became very popular. It suits software with planned, numbered releases that must support several versions at once, such as installed desktop software. In 2020 Driessen added a note to the original article. He wrote that for software that is delivered continuously, such as web applications, a simpler workflow is a better fit than Git Flow. Trunk-based development keeps one main branch, often called trunk. Developers merge small changes into it every day. Ask the class which model their teams use today, and how long their branches usually live. Sources: Driessen, V. (2010, note added 2020), "A successful Git branching model", nvie.com; Hammant, P., trunkbaseddevelopment.com.

Trunk-based development

  • Developers merge small changes into main at least once a day.
  • Unfinished features are hidden behind feature flags, so main can always be released.
  • High performers had three or fewer active branches, branches that lived less than a day, and no code freezes (Forsgren et al., 2018).
In trunk-based development the main branch is the integration point. Branches still exist, but only to hold a change while it is reviewed. The change is small enough to review in minutes and merge the same day. Large features are built in small steps. Code that is not ready for users is merged but switched off with a feature flag. Day 3 returns to feature flags as a release technique. The Accelerate research found that these branch habits predicted delivery performance. Teams with long-lived branches and code freezes performed worse, because integration was delayed and risky. Sources: Forsgren, Humble and Kim (2018), chapter 4; Hammant, P., trunkbaseddevelopment.com.

Pull requests and code review

1. Machine Verification

Automated CI
  • Automated builds: compilation & container packaging
  • Static analysis: linters, formatters, and type checkers
  • Test suites: unit, API, integration, and coverage checks
  • Machines check what machines can objectively prove.

2. Peer Review

Human Insight
  • Architecture & Intent: Is this the right solution?
  • Design & Readability: Maintainability, clarity, and edge cases
  • Test quality: Are we asserting the right business behaviours?
Microsoft Research (Bacchelli & Bird, 2013): Reviews catch far fewer syntax defects than expected. Their primary real-world value is knowledge transfer and shared code ownership.
The Small PR Golden Rule: Review turnaround speed and critical scrutiny drop precipitously as PR size grows. Keep pull requests scoped to single logical changes readable in under 20 minutes.
The pull request is where automation and people meet. The pipeline checks what a machine can check: the build, the tests, the lint rules. The reviewer checks what a machine cannot: whether the change is the right change, whether the design fits, whether the tests test the right thing. Bacchelli and Bird interviewed and surveyed developers at Microsoft and analysed review comments. Developers said finding defects was the main reason for review, but most comments were about code improvements and understanding. Review also spreads knowledge of the codebase across the team. Large pull requests are hard to review properly. Reviewers skim them and approve them. Keep pull requests to a size a colleague can read in about twenty minutes. Source: Bacchelli, A., and Bird, C. (2013), "Expectations, outcomes, and challenges of modern code review", ICSE 2013.

Continuous integration practices

  • Keep everything needed to build the software in version control.
  • Automate the build, and make the build test itself.
  • Everyone pushes commits to the main branch every day.
  • Every push to the main branch triggers a build.
  • Fix a broken build immediately. Keep the build under about ten minutes.

Fowler's article lists more practices. These five are the ones a pipeline enforces (Fowler, 2024).

Press ↓ for supporting detail: What is Continuous Integration?

Martin Fowler's article on continuous integration was first published in 2000, rewritten in 2006 and revised again in January 2024. It defines CI as a practice, not a tool: a team integrates its work frequently, and each integration is verified by an automated build with tests. A team that has a build server but merges once a month does not practise CI. The ten-minute build comes from Extreme Programming. If the build takes an hour, people stop waiting for it and push more changes on top of a broken build. The other practices in the article include hiding work in progress, testing in a clone of production, making the build status visible, and automating deployment. Source: Fowler, M. (2024), "Continuous Integration", martinfowler.com/articles/continuousIntegration.html.

Deep Dive / Core Concept

What is Continuous Integration?

The Practice

Social Contract

Developers merge working code into the shared main branch daily. Small, frequent merges eliminate painful "merge hell" and expose conflicts while they are still tiny.

The Tooling

Automated Gatekeeper

An automated server (like Harness) builds and tests every commit within ten minutes, giving immediate feedback on code health and preventing broken code from reaching others.

Key Insight

Having a build server is not CI. A team that runs automated builds but merges only once a month is doing automated builds, not Continuous Integration.

Explain Martin Fowler's classic distinction for BAs, QEs and mainframe engineers: CI is a team habit and social contract first, and an automated tool second. Without frequent daily integration into main, the automated tool only reports conflicts after they have already become large and painful.

Why integration delay is expensive

  • The longer two branches stay apart, the more both of them change, and the larger the conflicts.
  • A conflict found after three weeks involves code that its authors no longer remember well.
  • Integrating every day keeps each merge small and each problem easy to locate.
Integration effort does not grow in a straight line with time. Two developers who each change ten files a day overlap rarely in one day, but after three weeks their changes touch many of the same areas, and the combined change is too large to reason about. Teams used to call the weeks before a release "integration hell". Continuous integration removes that phase by integrating continuously. Ask the class if they have experienced a merge that took more than a day to resolve. Ask how big the branches were. Source: Fowler (2024), section "Integration Hell"; Humble and Farley (2010), chapter 3.

The deployment pipeline

A change moves to the next stage only if it passed the previous one (Humble and Farley, 2010).

Humble and Farley defined the deployment pipeline as the automated path every change takes from version control to production. The commit stage runs in minutes and catches most problems. It compiles or packages the code, runs unit tests and static analysis, and produces the artifact that later stages use. The acceptance stage runs slower tests against the built artifact. Later stages deploy the same artifact to environments closer to production. The pipeline also records evidence: for each version, which tests ran and which environments it reached. Today's labs build the first two stages. Lab 09 on Day 3 adds deployment, smoke tests, promotion and rollback. Source: Humble, J., and Farley, D. (2010), Continuous Delivery, chapter 5.

Build once, promote the same artifact

  • Build the artifact once, in the pipeline. Deploy that same artifact to every environment.
  • Only the configuration changes between environments. Keep configuration in the environment (Wiggins, 2011).
  • If you rebuild for production, you deploy something that was never tested.
An artifact is the output of the build: a JAR file, a Python wheel, or, in this course, a container image. The image is identified by a digest, a hash of its content, so you can prove that production runs the same image that dev tested. Rebuilding from the same commit is not the same thing: dependencies may have changed, and the build machine may differ. The Twelve-Factor App calls this separation "strict separation of config from code" and recommends environment variables for configuration. In Lab 09 the pipeline builds one image, tags it with the build number, deploys it to dev, tests it, and promotes the same image to production. Sources: Humble and Farley (2010), chapter 5; Wiggins, A. (2011), The Twelve-Factor App, factor III, 12factor.net.

Pipelines and Harness

Automated build stages, container steps, and triggers

Topic transition: Pipelines and Harness. This divider slide has zero allocated teaching time.

The parts of a pipeline

  • A trigger starts an execution: a push, a pull request, a tag, or a person selecting Run.
  • A pipeline has stages. A stage has steps that run in order. A failed step stops the stage.
  • The execution reports its status back to the commit and the pull request.

Press ↓ for supporting detail: Hierarchy of a pipeline

Use the vocabulary consistently from now on. A pipeline is the definition. An execution, or run, is one use of that definition for one commit. Each execution has a number, which the YAML can read as build.number. The clone step is added automatically. It fetches the commit that triggered the execution into the workspace. The steps you write run after it, in order. If any step fails, the stage stops and the execution reports failure. The status check is what branch rules use to allow or block a merge. Lab 03 depends on it. The Harness platform uses the same words: pipeline, stage, step, execution, trigger.

Deep Dive / Mental Model

Hierarchy of a Pipeline

1. Pipeline & Execution

Blueprint & Run

Pipeline: The reusable definition in code.
Execution: One specific run for a commit (e.g. build #42).

2. Stage

The Major Phase

A logical group of steps sharing a purpose (e.g. ci stage to build and test; deploy stage to release).

3. Step

The Single Action

An individual command or container task inside a stage (e.g. clone, lint, test). If any step fails, the stage stops immediately.

Manufacturing Analogy

Think of an assembly line: The pipeline is the factory floor design, the execution is one car passing through, the stages are assembly stations (frame, engine, paint), and the steps are individual operations at each station.

Clarify the terminology before Lab 02. Non-developers and mainframe engineers often ask what the difference is between a stage and a step, or why an execution is called a build or a run. In Harness YAML, kind: pipeline holds spec.stages, which hold spec.steps.

Pipeline as code

kind: pipeline
spec:
  stages:
  - name: build
    type: ci
    spec:
      steps:
      - name: test
        type: run
        spec:
          container: python:3.12-slim
          script: pip install -r requirements-dev.txt && pytest
  • The pipeline is a YAML (YAML Ain't Markup Language) file in the repository: .harness/ci.yaml.
  • A change to the pipeline is reviewed in a pull request, like a change to the code.
  • The history shows who changed the pipeline, when, and why.
Read the YAML from the top. kind: pipeline says what the file is. A pipeline has a list of stages. A ci stage has a list of steps. The step called test has type run, which means: start this container image and run this script inside it. Storing the pipeline next to the code has three benefits. The pipeline and the code that it builds always match, because they come from the same commit. Pipeline changes go through review. And an old commit can still be built with the pipeline that existed at that time. Older CI servers stored jobs in a web interface, so nobody could review or roll back a change to a job. In Lab 02 participants write this file themselves, one step at a time.

Containers as build environments

  • Each step names a container image, for example python:3.12-slim.
  • The image provides the tools. Nothing is installed on the machine that runs the pipeline.
  • Every execution starts from the same image, so a result can be repeated.
  • Pin the image tag. A floating tag such as latest can change between two runs.
  • Steps can use different images: Python for tests, Terraform for infrastructure, kubectl for deployments.

Press ↓ for supporting detail: Why run steps in containers?

Before containers, build servers had every tool installed on them: several versions of Java, Python, Node and so on. Teams fought over the versions, and a build that passed on one agent failed on another. With a container per step, each step declares its environment. The machine that runs the pipeline only needs Docker. The same image runs on a developer's laptop, so "it works on my machine" becomes easier to check: run the same image locally. Lab 02 does this. Participants run the tests in python:3.12-slim on their own machine before they write the pipeline. Pinning matters because tags are mutable. python:3.12-slim today and next month are different images. For full reproducibility you pin the digest, which Day 3 explains.

Deep Dive / Tool Isolation

Why Run Build Steps in Containers?

The Past

Snowflake Build Agents

Compilers and runtimes (Java 8, 11, 17; Python 2/3) installed globally on the build VM. Upgrades for Team A broke Team B's builds. "Passed on agent 1, failed on agent 2."

Modern CI

Disposable Toolboxes

Each step pulls an isolated, containerized image (e.g. python:3.12-slim). The build host only needs Docker. When the step exits, the container is destroyed without lingering side-effects.

Reproducibility Rule

Because the container image is identical on your laptop and in the pipeline, "it works on my machine" problems disappear: you can run the exact same container command locally.

For BAs, QEs and mainframe engineers who haven't worked with Docker yet: Explain that a container is just a packaged toolbox. We don't need Python installed on our lab server or laptop; Harness asks Docker to run python:3.12-slim just for the 30 seconds the test takes.

How Harness Open Source runs a step on your machine

Harness asks Docker to start one container per step. The steps reach Harness by the name harness on the devops network.

This is the setup participants built in Lab 01. Harness Open Source runs in one container. The Docker socket is mounted into it, so Harness can ask the Docker Engine on the lab machine to start other containers. For each execution Harness creates a workspace volume, starts a clone container that fetches the code from Harness over HTTP, and then starts one container per step with the workspace mounted. The devops network is a user-defined Docker network. Containers on it can reach each other by name, which is why the clone step can use http://harness:3000. On Day 2 the Kubernetes cluster joins the same network, so pipeline steps can reach it too. On the Harness platform the same job is done by Harness Cloud machines or by a delegate inside the company network.

Steps share the workspace

  • Each step runs in a new container, with its own filesystem.
  • Only the workspace is shared. To pass files to a later step, write them into the workspace.
This catches many people the first time. If step one runs pip install and step two runs pytest, step two fails with "pytest: command not found", because the package was installed in step one's container, and that container is gone. Two fixes: install and test in the same step, or install into a virtual environment inside the workspace, which later steps can activate. Lab 02 shows which of the two fixes its pipeline uses. The same model applies on the Harness platform. Each step in a CI stage shares the workspace; tools installed elsewhere do not persist. Ask the class: what happens to a file that the test step writes to /tmp?

Background services

- name: db
  type: background
  spec:
    container: postgres:17-alpine
    envs: {POSTGRES_PASSWORD: test}
- name: integration
  type: run
  spec:
    container: python:3.12-slim
    envs:
      DATABASE_URL: postgresql://postgres:test@db:5432/postgres
    script: pytest -m integration
  • A background step starts a service and keeps it running while the later steps run.
  • Later steps reach the service by the step name as host name: db.
  • The service stops when the stage ends.
Integration tests need real dependencies: a database, a cache, a message queue. A background step provides one for the length of the stage. Here the step called db starts Postgres 17. The integration test step connects to host db on port 5432. The database starts empty on every execution, so the tests do not depend on data left by an earlier run. The password is a throwaway value for a database that exists for two minutes, which is acceptable in a test pipeline. Day 2 covers real credentials. The test step must wait until Postgres accepts connections, because the database takes a few seconds to start. Lab 03 adds that wait.

Conditions and expressions

- name: report
  type: run
  when: build.event == "pull_request"
  spec:
    container: alpine:3.20
    script: echo "Run ${{ build.number }}; Commit ${{ build.commit }}"
- name: notify
  type: run
  when: failure()
  spec:
    container: alpine:3.20
    script: echo "An earlier step failed"
  • ${{ … }} inserts a value when the pipeline runs: the build number, commit, branch or event.
  • when: decides at run time whether a step runs.
  • failure() runs a step only after an earlier step failed. always() runs it in every case.
Expressions let one pipeline file behave differently for different events. build.number, build.commit, build.branch, build.event and build.target are among the values Harness Open Source provides. Conditions are expressions that evaluate to true or false. Operators include ==, !=, and, or, not, matches, contains and startsWith. A common use is to run tests on every event but deploy only for pushes to main. Lab 09 uses failure() to roll back a deployment when a smoke test fails. On the Harness platform the syntax is different, for example the expression <+pipeline.sequenceId>, but the idea is the same. Source: Harness Open Source documentation, "Conditions" and "Expressions", developer.harness.io.

The test pyramid

Write many small, fast tests and a few slow, broad ones (Cohn, 2009; Vocke, 2018). Higher layers cost more to write, run and maintain.

Start with why tests are automated at all. If a team deploys once a quarter, a week of manual testing is possible. If it deploys every day, every change needs the same checks in minutes, and only automation can do that. Mike Cohn described the pyramid in 2009. The idea is about proportion. Unit tests check one function or class in milliseconds, so you can have thousands. End-to-end tests drive the whole system and break when anything changes, so keep few of them for the main user paths. When a team has mostly end-to-end tests, the pyramid is upside down, a pattern sometimes called the ice-cream cone, and the suite is slow and fragile. Sources: Cohn, M. (2009), Succeeding with Agile, chapter 16; Vocke, H. (2018), "The Practical Test Pyramid", martinfowler.com.

Lab 02 runs the unit and API tests. Lab 03 adds the integration tests, with Postgres as a background service.

Describe the sample application. It is a small flight-status service written in Python with FastAPI. It stores flights with an origin, destination, departure time and status. Status changes follow rules: a flight can go from scheduled to boarding, but not from arrived back to boarding. Those rules are pure logic and have unit tests. The API tests start the application in the test process with an in-memory store and send HTTP requests to it. The integration tests use a real Postgres database to check the SQL. They are slower and need a database, so they run only when one is available. Ask: which of these tests would catch a typo in an SQL query? Only the integration tests.

Test doubles

DoubleWhat it does
DummyFills a parameter that the test does not use.
StubReturns fixed answers to calls.
SpyA stub that also records how it was called.
MockFails the test if the expected calls did not happen.
FakeA working but simpler implementation, such as an in-memory database.

The flight-status API tests use a fake, an in-memory store, in place of Postgres (Meszaros, 2007).

A test double replaces a real dependency in a test, the way a stunt double replaces an actor. Gerard Meszaros named the five kinds in xUnit Test Patterns. People often call all of them mocks, but the difference matters. Stubs and fakes support state-based testing: you check the result. Mocks support behaviour-based testing: you check the calls. Tests with many mocks break when the implementation changes, even if the behaviour is still correct. The fake store in the sample app has the same interface as the Postgres store. That design makes the API tests fast, and the integration tests check that the Postgres store behaves the same way. Source: Meszaros, G. (2007), xUnit Test Patterns, chapter 11.

Flaky tests

Definition A test that passes and fails on the exact same commit without any code changes.
1. Timing & Sleep Fixed timeouts, slow CI runners, async race conditions
2. Shared State Polluted test DBs, leftover static state, shared caches
3. Test Order Tests pass when run alone, fail when run in sequence
4. External Calls Unmocked network APIs, external DNS, time-of-day

Google CI Scale (Micco, 2016)

While only ~1.5% of test runs report flaky failures, almost 16% of all test cases exhibit flakiness across their lifecycle—generating thousands of false alarms daily.

The "Cry-Wolf" Trap & Remediation

Flaky tests train developers to ignore failures and re-run pipelines until green. Golden Rule: Fix or quarantine (isolate from the blocking gate) immediately to preserve trust in CI.

A test suite is only useful if a failure means something. When failures are random, people stop reading them. John Micco reported Google's numbers in 2016. With millions of test runs a day, a 1.5% flaky rate produces thousands of false failures daily. In the labs, the integration tests could be flaky if they started before Postgres was ready. Lab 03 avoids this by waiting until the database accepts connections, instead of sleeping for a fixed number of seconds. Quarantine means moving the test out of the blocking suite, with a ticket to fix it, so it does not block everyone while it is broken. Source: Micco, J. (2016), "Flaky Tests at Google and How We Mitigate Them", Google Testing Blog.

What code coverage tells you

def can_board(status):
    return status in ("SCHEDULED", "DELAYED")

def test_can_board():
    can_board("SCHEDULED")      # runs the line, checks nothing
  • Coverage measures which lines ran during the tests. This test reaches 100% coverage of can_board.
  • Coverage does not measure whether the tests check the results.
  • In five large Java programs, coverage had a low to moderate correlation with fault detection once the number of tests was held constant (Inozemtseva and Holmes, 2014).
  • A coverage threshold is still useful as a floor that blocks large untested changes.
Coverage tools record which lines execute during the test run. The test on the slide calls the function and asserts nothing, yet the coverage report shows the function as fully covered. Inozemtseva and Holmes used mutation testing: they inserted small faults into the programs and checked how many each test suite detected. More tests detected more faults, but coverage on its own was not a strong predictor. Use coverage to find code that no test runs at all. Do not treat a high number as proof of good tests. In Lab 03 the pipeline fails if coverage drops below a threshold. The threshold blocks a pull request that adds code with no tests. Source: Inozemtseva, L., and Holmes, R. (2014), "Coverage is not strongly correlated with test suite effectiveness", ICSE 2014.

Pipeline Optimization Rule: Fastest checks run first. Static analysis completes in seconds without provisioning databases or containers—catching typos and security flaws before expensive integration tests run.
Static analysis complements tests. Tests check behaviour for the inputs someone thought of. Static analysis checks every line for known categories of problems, whether or not a test reaches it. Ruff is a Python linter and formatter. It checks hundreds of rules in well under a second for a project of this size. Ordering matters in a pipeline. Put the fastest checks first, so a typo fails the pipeline in seconds instead of after a five-minute test run. Security scanners for source code, dependencies and container images follow the same idea. Day 3 adds a container image scan. Ask the class which static analysis tools their teams already use, for example SonarQube or a language linter.

Finding problems earlier

"Shift left" means moving checks toward the start of this line. A problem found in the editor costs one person a few seconds. The same problem found in production affects customers.

The term shift left comes from drawing the delivery process from left to right, as on the slide. The later a problem is found, the more people it affects and the more work has already been built on top of it. You will hear claims that a bug costs a hundred times more in production. Those exact numbers are hard to trace to good evidence, so do not quote them. The direction of the effect is not disputed. Shift left does not mean removing later checks. It means adding fast, cheap checks early, so the later checks find less. Today's lab works in the highlighted step: the pull request pipeline. Developers can run the same lint and tests locally before they push, which moves the check one step further left.

Quality gates on the main branch

  • A branch rule on main blocks direct pushes and requires a pull request.
  • The rule names the ci status check. Merge is possible only after the latest run of ci passed.
A quality gate is a condition a change must meet before it moves on. In Harness Open Source the gate for main is a branch rule. The rule blocks direct pushes, so every change arrives through a pull request. It requires the status check named after the pipeline to succeed. When the check fails, the merge button is disabled and the pull request shows which rule is not met. When the developer pushes a fix, the pull request trigger runs the pipeline again, and the merge becomes possible after a green run. Rules can also require approvals from reviewers or code owners. In Lab 03 participants work alone, so approval is a "Going further" task. The Harness platform and other Git hosts offer the same kind of rule, sometimes called branch protection.
