Containers and Docker

Images, layers, isolation, and registries

What to Say: We begin our first major topic of the day: Containers and Docker. We will demystify what a container actually is at the Linux kernel level, understand why image layers make builds fast and immutable, and explore how to secure the container software supply chain.

Teaching Focus: Transition smoothly into foundational container theory, framing containers as kernel-level process isolation rather than mini-VMs.

Virtual machines and containers

A virtual machine runs its own kernel on virtual hardware. A container is a group of ordinary processes on the host kernel, with an isolated view of the system.

Press ↓ for supporting detail: Containers vs. Virtual Machines

What to Say: When engineers first encounter containers, they often think of them as tiny, lightweight virtual machines. But architecturally, they are completely different. A virtual machine uses a hypervisor to emulate physical hardware and boots an entire independent guest kernel with its own system daemons, taking minutes to start and gigabytes of memory.

Linux Architecture: A container is simply an ordinary group of Linux processes running directly on the shared host kernel. The container engine sets boundaries using kernel namespaces and control groups. Because there is no guest operating system booting, a container launches in milliseconds and consumes almost zero overhead.

Ask the Room: When an application running in a container crashes or experiences high CPU, what tools do you reach for to inspect it—host-level tools like top and ps, or container engine commands?

Teaching Focus: Demystify the architectural difference between hardware emulation via hypervisors and process isolation on a shared Linux kernel.

Reference only

Deep Dive / Isolation Model

Containers vs. Virtual Machines

Virtual Machines

Hardware Virtualization

A hypervisor runs multiple complete operating systems on virtualized hardware. Each VM runs its own independent guest kernel, system daemons, and gigabytes of disk/memory, taking minutes to boot.

Containers

Operating System Virtualization

Containers are ordinary Linux processes sharing the single host kernel. Namespaces partition what processes see (network, mounts, PIDs); cgroups restrict what resources they consume.

Performance & Portability

Because containers share the host kernel, they start in milliseconds and consume megabytes rather than gigabytes. The exact same image runs identically on a developer laptop, CI server, or Kubernetes cluster.

What to Say: For everyone joining us from quality engineering, analysis, or mainframe backgrounds, here is a practical mental model: think of a virtual machine like a standalone single-family house with its own separate foundation, plumbing, furnace, and electrical wiring. Think of a container like an individual apartment in a modern high-rise.

Security & Trade-offs: Each apartment has its own locked front door and private rooms, but everyone shares the building's central water mains, foundation, and heating plant. That shared foundation is the Linux kernel. It gives us incredible speed and density, which is why CI pipelines can spin up dozens of test environments per minute, but it also means host kernel security and patching remain critical.

Linux namespaces isolate what a process can see

PID Namespace

Processes

Own process hierarchy. The container's primary process runs as PID 1, receiving signals like SIGTERM.

Net Namespace

Network

Private virtual interfaces, IP routing tables, firewall rules, and container-specific port allocations.

Mount Namespace

Filesystem

Isolated filesystem root constructed from container image layers, private from host disk paths.

UTS Namespace

Hostname

Independent system hostname and domain name, preventing conflicts across shared node hosts.

IPC Namespace

Inter-Process

Private POSIX/System V message queues, semaphores, and shared memory segments.

User Namespace

Privilege

Maps container root (UID 0) to an unprivileged host UID, mitigating kernel breakout risks.

Operating System Reality: Containers are not lightweight virtual machines — they are standard host processes partitioned by Linux kernel namespaces.

What to Say: The magic of container isolation rests on Linux namespaces. If you remember one principle today, let it be this: namespaces control what a process can see. When a process starts inside a container, the kernel assigns it private namespaces that act like blinders.

Namespace Reality: In the PID namespace, the container process thinks it is PID 1, the root of the universe, even though on the host it might be PID 48291. In the network namespace, it sees only its own virtual eth0 and private port bindings. And critically, in standard Docker setups, root inside the container is root on the host kernel unless user namespace remapping or a dedicated non-root user is configured.

Ask the Room: Why is running container processes as root (UID 0) considered such a severe vulnerability in enterprise Kubernetes clusters?

Teaching Focus: Detail the six fundamental Linux namespaces and explain why unprivileged user execution is necessary to prevent kernel breakouts.

Control groups limit what a process can use

CPU Enforcement

Compressible
  • • When a container reaches its limit, the Linux kernel throttles it.
  • • Process remains running; latency increases without crashing.
  • • Slow responses without restarts often indicate CPU throttling.
docker run --cpus 0.5 ...

Memory Enforcement

Incompressible
  • • When a container exceeds its limit, the kernel OOM killer terminates it.
  • • Process dies immediately with exit code 137 (OOMKilled).
  • • Memory leaks in applications trigger repeated container crash loops.
docker run --memory 256m ...
Monitoring & Kubernetes Translation: Inspect real-time cgroup counters with docker stats. Kubernetes requests and limits configure these exact same Linux cgroup settings.

What to Say: If namespaces govern what a process can see, control groups, or cgroups, govern how much of the system it is allowed to consume. Developed originally at Google under the name process containers, cgroups prevent any single workload from starving its neighbors of CPU or memory.

Compressible vs Incompressible: Notice the crucial operational distinction between the two resources. CPU is compressible: if a process tries to use more CPU than its limit, the kernel throttles it. It runs slower and latency spikes, but it doesn't crash. Memory is incompressible: if an application exceeds its memory limit, the Linux kernel out-of-memory killer steps in and terminates it instantly with exit code 137.

Ask the Room: If a backend service has a slow memory leak, what will you see in production—increased request latency, or repeated OOMKilled restarts?

Teaching Focus: Contrast compressible CPU throttling with incompressible memory termination (OOMKilled exit code 137) to prepare for Kubernetes QoS.

Images are stacks of read-only layers

Each Dockerfile instruction that changes files adds a read-only layer. OverlayFS stacks the layers into one filesystem and adds a writable layer for each container.

What to Say: Let's look at how container images are stored and assembled. An image is not a single monolithic virtual hard drive. It is a stack of immutable, read-only tar archives called layers, each identified by a SHA-256 cryptographic digest.

Copy-on-Write: When a container starts, the storage driver creates a thin, writable layer on top. If the running process modifies a file from a lower layer, OverlayFS uses copy-on-write to copy that file up into the writable layer before editing. If you delete a file in a later Dockerfile step, it only places a whiteout marker in the top layer—the bytes remain permanently trapped in the underlying layer.

Key Insight: This is why you must never put secrets into an image and try to delete them in a subsequent RUN instruction. In Lab 07, you will use docker history to inspect each layer and see exactly what was cached.

Teaching Focus: Explain layer stacking, copy-on-write mechanics, and why deleted files or secrets persist in lower immutable layers.

Tags and digests

k3d-registry.localhost:5000/flight-status:1.4.0
k3d-registry.localhost:5000/flight-status@sha256:9b1e5c0d…
  • A tag is a name that points to an image. Anyone with push rights can point it at a different image.
  • A digest is the SHA-256 (Secure Hash Algorithm, 256-bit) hash of the image manifest. It identifies one image and cannot change.
  • latest is the default tag name. It does not mean the newest image.
  • Deploy by digest, or by a tag that your pipeline never reuses.

What to Say: Here is one of the most critical operational lessons for production delivery: the difference between an image tag and an image digest. A tag is merely a mutable human-readable pointer. Anyone with push privileges to a registry can overwrite tag 1.4.0 with completely different code.

The Danger of Tags: If a tag is overwritten, two servers in the same cluster could pull different code under the identical tag name, making debugging an absolute nightmare and rendering rollbacks unreliable. A digest, on the other hand, is the immutable SHA-256 hash of the image manifest. It is mathematically impossible to change the image contents without changing the digest.

Ask the Room: If you specify image: python:latest in your Dockerfile or deployment manifest, what risks does that introduce into your build pipeline?

Teaching Focus: Emphasize artifact immutability, contrasting mutable tags with cryptographic digests, and introduce ECR tag immutability.

Dockerfile practices

Minimal Base Image

Attack Surface

Start with python:3.12-slim over full OS images. Fewer preinstalled packages means faster pulls and a drastically smaller CVE footprint.

Smart Layer Caching

Build Speed

COPY requirements.txt and run pip install before copying source code. Prevents re-installing all dependencies on every commit.

Least Privilege User

Runtime Security

Explicitly run as non-root USER 10001. Prevents container breakout vulnerabilities from executing with root privileges on the host kernel.

Build Context Hygiene

Hygiene

Maintain strict .dockerignore rules excluding .git, test artifacts, virtual environments, and local .env credential files.

Twelve-Factor Operational Rule: Run a single main process per container and stream all application logs directly to stdout and stderr.

What to Say: Writing a Dockerfile is easy, but writing a production-grade, secure, high-performance Dockerfile requires strict discipline. Every line in this matrix addresses a real-world production incident.

Best Practices Breakdown: We start with a minimal base image like python:3.12-slim to slash CVE vulnerabilities and reduce image size. We leverage layer caching by copying requirements.txt and running pip install before copying source code, ensuring dependency builds are cached. We drop privileges to a non-root UID 10001, and we maintain an aggressive .dockerignore file to prevent accidental leaks of .git history or local .env secrets.

Twelve-Factor Rule: Finally, always design containers to run a single foreground process and stream logs to stdout and stderr so the platform can aggregate them cleanly.

Teaching Focus: Walk through the four pillars of Dockerfile engineering: minimal base images, cache ordering, least-privilege users, and build context hygiene.

A Dockerfile for a Python web service

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY flightstatus/ ./flightstatus/
RUN useradd --uid 10001 --no-create-home app
USER 10001
EXPOSE 8000
CMD ["uvicorn", "flightstatus.main:app", "--host", "0.0.0.0", "--port", "8000"]
  • Dependencies are installed before the code is copied, so a code change reuses the cached dependency layer.
  • The server runs as user 10001, which has no special rights on the host.

What to Say: Let's walk through the actual Dockerfile you will author for our flight-status service in Lab 07. Notice the deliberate structure: we set the working directory, copy requirements.txt, and run pip install with --no-cache-dir so wheel cache files don't bloat the image layer.

Code Walkthrough: Only after dependencies are installed do we copy our application code. Then we create an unprivileged user named app with UID 10001 and switch to it using the USER instruction. Notice also the JSON array syntax for CMD: ["uvicorn", ...]. Using the JSON syntax ensures uvicorn runs directly as PID 1, allowing it to receive SIGTERM signals immediately when the container is stopped.

Software bills of materials and vulnerability scanning

Tier 1 · Catalog

The Ingredient List (SBOM)

A machine-readable catalog (CycloneDX or SPDX) documenting every OS package and language dependency version in the image without rebuilding.

Tier 2 · Scan

Automated CVE Matching

Scanners like Trivy cross-reference SBOM packages against CVE databases (NVD, GitHub Advisories) to identify vulnerabilities with assigned severities.

Tier 3 · Gate

Actionable Policy Enforcement

Enforce pipeline gates on actionable findings: fail CI builds on CRITICAL issues with available upstream patches (using --ignore-unfixed).

The Continuous Vulnerability Clock: An image with zero CVEs today will develop CVEs tomorrow as new exploits are published — continuous re-scanning of deployed images is mandatory.

What to Say: Software supply chain security is no longer optional. A Software Bill of Materials, or SBOM, is essentially a detailed ingredient list of every operating system package and third-party library bundled inside your container.

Funnel Strategy: In Lab 07, you will use Trivy to generate a CycloneDX SBOM and perform automated vulnerability scanning. But here is the golden rule for pipeline gates: fail builds only on actionable findings using the --ignore-unfixed flag. If an advisory has no available upstream patch, failing the pipeline just frustrates developers without improving security.

Key Insight: Also remember that an image with zero vulnerabilities today will inevitably have CVEs discovered next month—continuous scanning of deployed images in your registry is essential.

Teaching Focus: Detail the SBOM supply chain funnel (catalog, scan, gate) and teach actionable vulnerability gating using --ignore-unfixed.

Signing and provenance

  • A signature shows who published an image and that it has not changed since.
  • Sigstore's cosign signs an image digest and stores the signature in the registry next to the image.
  • Provenance records how an image was built, including the source commit, the build system and the build steps.
  • Supply-chain Levels for Software Artifacts (SLSA) Build levels 1 to 3 ask for provenance, then provenance signed by a hosted build platform, then a hardened build platform.
  • A cluster admission policy can refuse images that are not signed by a trusted key.

What to Say: Vulnerability scanning answers what is inside an image. Signing and provenance answer where it came from and who authorized it.

Cryptographic Trust: Using tools like Sigstore cosign, a CI/CD pipeline cryptographically signs the image digest immediately after pushing it to the registry. The SLSA framework—Supply-chain Levels for Software Artifacts—defines verifiable standards for proving that an image was built on an authentic, tamper-resistant platform from a verified Git commit.

Production Guardrail: In advanced enterprise clusters, Kubernetes admission controllers reject any pod whose container image lacks a valid cryptographic signature from an approved internal key.

services:
  app:
    build: .
    ports:
      - "8000:8000"

      DATABASE_URL: postgresql://flights:flights@db:5432/flights

  db:
    image: postgres:17-alpine

Compose creates one network for the project, and each service is reachable by its name. The API reaches the database at the host name db.

What to Say: Rarely does an application run completely alone. Our flight-status service requires a PostgreSQL database to store flight schedules and updates. Docker Compose allows us to declare both containers, their shared network, and environment variables in a single compose.yaml file.

Networking & Health: When you run docker compose up, Compose automatically provisions a private bridge network and registers DNS names matching the service keys. The app reaches the database simply by querying the hostname db.

Common Pitfall: Notice depends_on: db. By default, depends_on only waits for the database container to start, not for PostgreSQL to actually accept connections! In Lab 07, you will add a healthcheck condition so the app doesn't crash on startup.

Amazon ECS concepts

A task definition is a versioned JSON document. A task is one running copy of it, and a service keeps the desired number of tasks running.

What to Say: Now let's see how these same multi-container concepts translate to AWS through Amazon Elastic Container Service. Four fundamental concepts govern ECS architecture.

Concept Breakdown: A task definition is an immutable, versioned JSON document specifying your containers, memory, CPU, environment variables, and secrets. A task is a running instantiation of that definition. An ECS service maintains the desired task count, manages health checks, and registers tasks with a load balancer. And an ECS cluster is the logical administrative boundary grouping them together.

Kubernetes Analogy: For those familiar with Kubernetes, an ECS task definition maps to a Pod template, a task maps to a Pod, and an ECS service combines the roles of a Deployment and a Service.

Teaching Focus: Walk through the four core Amazon ECS concepts (task definition, task, service, cluster) and provide the direct Kubernetes analogy.

What changes when the task runs in AWS

  • Each Fargate task gets its own network interface and private IP address in a virtual private cloud (VPC) subnet.
  • The task execution role lets ECS pull the image and read secrets. The task role is what the application uses to call AWS APIs.
  • An Application Load Balancer sends requests to healthy tasks. It replaces the port mapping on your machine.
  • The database is a managed service such as Amazon Relational Database Service (RDS).
  • Logs go to Amazon CloudWatch Logs.

What to Say: When you move a container workload from your laptop into AWS, the container image itself remains 100% identical—that is the beauty of OCI compliance. But the infrastructure surrounding that image changes significantly.

Roles & Infrastructure: Pay close attention to the two distinct IAM roles: the task execution role is used by the AWS ECS agent before your container starts to pull the image from ECR and fetch secrets from Secrets Manager. The task role is used by your running application code to interact with AWS services like S3 or DynamoDB. Keeping these separated ensures least-privilege security.

Production Perimeter: Furthermore, local host port bindings are replaced by an Application Load Balancer, and local container databases are replaced by managed Amazon RDS instances.

Teaching Focus: Clarify the critical distinction between the ECS Task Execution Role and Task Role, and explain AWS surrounding infrastructure (ALB, RDS, VPC).

Deployments, ReplicaSets and Pods

A Pod is one or more containers that share an IP address and volumes. A Deployment creates a new ReplicaSet for each new Pod template, scales the old one to zero and keeps it for rollback.

Pods & Revisions: A Pod is the smallest deployable unit—one or more containers sharing an IP address and localhost network. A ReplicaSet ensures that an exact number of identical Pods remain healthy. But in practice, you almost never create ReplicaSets directly. You declare a Deployment.

Services and Ingress

A Service gives a set of Pods one stable name and address, and sends traffic only to Pods that pass their readiness probe. An Ingress routes HTTP requests to Services by host name and path.

Press ↓ for supporting detail: Why do we need a Service?

What to Say: Pods in Kubernetes are ephemeral: they scale up, scale down, crash, and reschedule, and every time a new Pod starts, it gets a completely new dynamic IP address. If clients attempted to connect directly to Pod IPs, every deployment would trigger a massive connection outage.

The Role of Services: A Kubernetes Service provides a permanent, stable virtual IP and DNS name within the cluster. It selects Pods using label selectors (like app: flight-status) and routes traffic only to Pods currently passing their readiness probes.

Ingress Routing: An Ingress sits in front of Services, acting as a Layer 7 HTTP router that routes incoming domain names and paths to internal Services. In our lab, k3d uses an embedded Traefik ingress controller, whereas in Amazon EKS, the AWS Load Balancer Controller provisions an Application Load Balancer.

Liveness, readiness and startup probes

Startup Probe

Initialization Guard

“Has the application finished starting up?”

Pauses liveness and readiness checks until passing. If it fails past threshold, kubelet restarts the container. Protects slow-starting services from premature termination.

Liveness Probe

Deadlock Recovery

“Is the process deadlocked, crashed, or hung?”

Kubelet terminates and restarts the container immediately. Keep checks strictly internal (/health) — never check external databases here!

Readiness Probe

Traffic Gatekeeper

“Can this Pod safely accept incoming traffic right now?”

Removes Pod from Service endpoints without restarting. Enables zero-downtime rolling updates (/ready tests internal readiness and database connectivity).

Core Architectural Rule: Liveness restarts the process; Readiness controls traffic routing.

What to Say: Health probes are how Kubernetes monitors application vitality. There are three types of probes, and confusing them causes severe production outages.

The Golden Rule: Memorize this golden rule: liveness restarts the process; readiness controls traffic routing. A liveness probe checks if your process is deadlocked or hung—if it fails, the kubelet terminates and restarts the container. Never check external dependencies like databases in a liveness probe, or a database glitch will trigger a catastrophic restart storm across your entire cluster!

Readiness & Startup: A readiness probe checks if the pod can safely serve customer traffic right now. If it fails, the Pod is quietly removed from the Service endpoint pool while staying alive. And startup probes protect slow-starting applications from premature liveness termination during initial boot.

Ask the Room: What happens to a rolling update if a newly deployed pod fails its readiness check?

Teaching Focus: Teach the critical operational rule: liveness restarts processes, readiness routes traffic; warn against external dependency checks in liveness probes.

Requests, limits and quality of service

Requests · Scheduling Floor

Minimum CPU and memory reserved for the container. kube-scheduler sums requests to place Pods only on nodes with verified unreserved capacity.

Limits · Runtime Ceiling

Hard maximum capacity enforced via Linux cgroups. CPU usage is throttled; memory spikes beyond limits trigger immediate kernel OOMKilled termination.

Guaranteed

Top Priority

requests == limits for all containers. Highest stability; evicted last under node memory pressure.

Burstable

Standard

requests < limits. Allowed to burst above floor; evicted based on memory over-subscription.

BestEffort

Lowest

No requests or limits specified. High eviction risk; first to be terminated when node memory runs low.

Resource Sizing Discipline: Always specify both requests and limits — prevents noisy-neighbor CPU starvation and satisfies cluster ResourceQuotas.

What to Say: Here is where the cgroups we discussed this morning connect directly to Kubernetes manifest configuration. Every container should define two pairs of resource values: requests and limits for both CPU and memory.

Requests vs Limits: Requests represent the scheduling floor. The kube-scheduler sums container requests on a node to ensure it never overcommits capacity. Limits represent the hard runtime ceiling enforced by the Linux kernel. Exceeding CPU limits results in throttling; exceeding memory limits results in an instant OOMKilled termination.

QoS Classes: Depending on how you configure these, Kubernetes assigns one of three Quality of Service classes: Guaranteed, Burstable, or BestEffort. In Lab 08, setting requests and limits is mandatory to satisfy the namespace ResourceQuota we established in Lab 04.

Teaching Focus: Explain resource requests (scheduling floor) versus limits (runtime ceiling) and connect them to Kubernetes QoS classes and namespace quotas.

A rolling update, step by step

Settings: 4 replicas, maxSurge 1, maxUnavailable 0. There are never fewer than 4 ready Pods or more than 5 Pods. The dashed Pod has started but is not ready yet.

What to Say: Let's trace how Kubernetes performs a zero-downtime rolling update. By default, Deployments use two parameters: maxSurge and maxUnavailable.

Step-by-Step Flow: In this example with 4 replicas, maxSurge 1, and maxUnavailable 0, Kubernetes guarantees there are never fewer than 4 healthy pods serving traffic. In step 2, it launches one new version 1.5.0 Pod, bringing total pods to 5. It waits for that pod's readiness probe to pass. Only when the new pod is green does it terminate one old 1.4.0 pod, returning the count to 4. This sequence repeats until all pods run version 1.5.0.

Failure Safety: If the new version fails its readiness probe, the rollout halts immediately at step 2. The four original pods continue serving user traffic without dropped requests.

Role-based access control

A Role allows verbs on resource types in one namespace, and a RoleBinding grants the Role to a user, group or ServiceAccount. RBAC rules only add permissions, so anything a Role does not list is refused.

What to Say: Here is the security architecture that protects our Kubernetes cluster from unauthorized access. Kubernetes Role-Based Access Control, or RBAC, links an identity to specific permissions.

RBAC Mechanics: A ServiceAccount represents a machine identity—like our automated deployer account from Lab 06. A Role defines allowed API verbs (such as get, list, create, patch) on specific resource types within a single namespace. A RoleBinding connects the ServiceAccount to that Role.

Additive Security: Remember that Kubernetes RBAC is strictly additive: there are no explicit deny rules. If a permission is not explicitly granted by a bound Role, the API server rejects the request immediately. In Lab 09, our Harness pipeline authenticates using this exact scoped deployer credential.

Continuous delivery and continuous deployment

Continuous delivery keeps every change that passes the pipeline ready to release at any time (Humble and Farley, 2010). Continuous deployment releases each of those changes automatically.

The Core Distinction: In Continuous Delivery, every commit that passes automated testing and security gates is automatically deployed to pre-production environments and kept continuously releasable. However, the final promotion to production is a deliberate business decision—often requiring a single human click or approval window.

Straight Through to Production: In Continuous Deployment, there is zero human intervention—every passing commit flows straight through into production automatically, relying entirely on telemetry-driven canary analysis and automated rollbacks.

Build once, promote the same artifact

The image that passed the checks in dev is the image that runs in prod. Settings that differ between environments come from the environment, as variables and Secrets (Wiggins, 2011).

What to Say: If there is one cardinal rule of modern continuous delivery, it is this: only build your binaries once! Jez Humble and Dave Farley made this a cornerstone of their seminal work.

Why Rebuilding is Dangerous: If your pipeline rebuilds a container image for dev, rebuilds another image for staging, and builds a third image for production, you have violated artifact integrity. Even if the code didn't change, a downstream dependency might have been updated, a base image layer could differ, or a compiler flag might vary.

The Promotion Standard: You must build the container image once in CI, scan it, tag it with the immutable commit SHA and digest, deploy that exact image to dev, and promote the identical image digest to production. Only configuration—such as database connection strings and replica counts—changes across environments.

Teaching Focus: Instill the 'build once, promote everywhere' rule, explaining why rebuilding artifacts per environment destroys test validity.

Rolling and blue-green deployments

A rolling deployment needs little extra capacity but runs two versions side by side for a while. Blue-green needs two full environments and rolls back by switching traffic back (Fowler, 2010).

What to Say: When releasing a new version to production, you have several deployment strategies, each with distinct trade-offs between infrastructure cost and release speed.

Comparing Strategies: A rolling deployment, which you practiced in Lab 08, gradually replaces old pods with new ones. It requires minimal extra cluster capacity, but during the rollout, both versions run concurrently, meaning your database schema must remain backward-compatible.

Blue-Green Mechanics: Blue-green deployment spins up a completely duplicate environment—green—running the new version alongside the current blue environment. You run smoke tests against green in isolation, and when satisfied, switch the router or load balancer instantly. Rollback is as fast as flipping the switch back, but it requires double the compute infrastructure during deployment.

Teaching Focus: Compare rolling updates with blue-green deployments, analyzing infrastructure capacity costs, traffic transition speed, and database compatibility requirements.

Canary releases

A canary release sends a small share of real traffic to the new version and compares it with the current version before sending more (Sato, 2014). With plain Kubernetes, the split follows the Pod count.

What to Say: A canary release is the gold standard for high-traffic, mission-critical systems. Borrowing the metaphor from coal miners who used canaries to detect toxic gases, this technique routes a tiny slice of real production traffic—say 5 or 10 percent—to the new version.

Automated Evaluation: While the canary runs, monitoring systems compare its telemetry—error rates, latency, and CPU usage—against the baseline version. If the metrics look healthy, the traffic allocation gradually expands to 25, 50, and 100 percent. If errors spike, traffic immediately snaps back to the stable version, ensuring only a tiny fraction of users experienced the defect.

Enterprise Orchestration: Plain Kubernetes can approximate a canary by adjusting pod counts, but enterprise platforms like Harness Continuous Verification automate the statistical analysis and rollback decisions.

Teaching Focus: Explain canary deployment architecture, statistical metric comparison against baseline workloads, and automated traffic shifting.

Automated verification and rollback

A smoke test calls the new version the way a user would: a health check, a version check, one real request. The Lab 09 smoke test checks the version through the ingress; a "Going further" task adds the other two. A step with when: failure() rolls back when any earlier step fails.
